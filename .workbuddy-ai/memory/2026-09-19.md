### 2. 桌面版：多 IM 适配（关键实测结论）

各客户端输入框的 UIA 暴露方式完全不同，新增 `mjegg/im_targets.py` 做适配：

| 客户端 | 进程 | 输入框类名 | 控件类型 | 读文本 | match |
|---|---|---|---|---|---|
| 钉钉 | DingTalk.exe | `im_chat::InputRichTextEdit` | Edit | ValuePattern | exact |
| 微信 4.x | Weixin.exe | `mmui::ChatInputField` | Edit | ValuePattern | exact |
| QQ NT | QQ.exe | `ExEditor-qq-msg-editor` | Group(ProseMirror) | 遍历子 Text | **contains** |

**踩坑记录（都很隐蔽，下次直接复用结论）：**

1. `Control(ClassName=...)` 搜出来的是**基类 Control**，没有 `GetValuePattern` 之类的方法，
   会导致微信输入框永远读到空串。必须用 `Control.CreateControlFromElement(node.Element)`
   按真实控件类型重建一次。
2. QQ 编辑器的 ClassName 是整串 `ProseMirror ExEditor-qq-msg-editor is-empty`，
   其中 `is-empty` 随输入状态增减，所以**只能用子串匹配**，不能全等。
3. QQ 是 Chromium 壳，**默认不构建无障碍树**（整棵树只有 13 个节点）。
   向 render widget 发 WM_GETOBJECT 无效（主窗口的 render host 不是独立 HWND）；
   实测有效的是 `SetForegroundWindow(主窗口)` + 一次 UIA 树访问，之后整棵树变 618 节点。
   实现里只在"该进程本来就是前台"时才调用，避免抢用户焦点。
4. `os.exe`/`TabTip.exe` 都需要提权才能启动，没法用脚本直接拉起做取证；
   Win11 触摸键盘可以从任务栏托盘图标点开（约 1555,1048）。
5. 屏幕键盘（osk / TabTip）都是 `SendInput` 注入，实测带 `LLKHF_INJECTED(0x10)`、
   `dwExtraInfo == 0`。所以旧的 `ignore_injected_keys: true` 会把屏幕键盘一起挡掉。

### 3. 桌面版：注入按键策略（新增）

`ignore_injected_keys`(bool) → `injected_key_policy`：`ignore` / `unsigned` / `auto` / `allow`。
默认 `auto` = 接受 `dwExtraInfo==0` 的注入，**或**检测到屏幕键盘进程正在运行（`screen_keyboard_processes`）
时接受全部注入。屏幕键盘进程由 watcher 线程每 2 秒探测一次写进 `hook.screen_keyboard_active`，
钩子回调只读布尔量，不做系统调用。

同时把键盘缓冲兜底从"尾部 2/4/6/8 位模糊匹配"改成**整串匹配**：
旧逻辑会让 `amj` 因为结尾是 `MJ` 误触发（原规则里 `amj` 不该触发）。
配合 `ime.py` 的输入法组合态检测（`ImmGetCompositionString`），
组合态回车判为"上屏"，把缓冲搬到 `vk_pending` 保留，等真正的发送键到来。
